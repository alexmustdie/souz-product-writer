# Черновики товарных карточек для B2B-магазина

Локальный прототип на Python: принимает JSON товара, вызывает DeepSeek API и возвращает карточку в JSON или Markdown. Результат содержит SEO-заголовок, описание, характеристики, поисковые запросы, блок для менеджера и список недостающих сведений.

Технические характеристики копируются из входа программно. Модель пишет только текстовые поля; они проходят локальные проверки и отдельную проверку фактов той же LLM. Результат всегда остается черновиком для проверки человеком.

## Быстрый запуск

Требуется Python 3.11+ и ключ **DeepSeek API** с доступом к модели. Подписка на веб-чат сама по себе не заменяет API-ключ. Ключ OpenAI не нужен: библиотека `openai` используется как совместимый клиент к `https://api.deepseek.com`.

В PowerShell:

```powershell
git clone https://github.com/alexmustdie/souz-product-writer.git
cd souz-product-writer
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -c constraints.txt -e ".[test]"
Copy-Item .env.example .env
notepad .env
```

В `.env` заполнить `DEEPSEEK_API_KEY`. Файл включен в `.gitignore`; не отправляйте его вместе с проектом. По умолчанию используется `deepseek-flash`. Модель можно заменить через `DEEPSEEK_MODEL` или `--model`. Переменные окружения имеют приоритет над `.env`.

```powershell
.\.venv\Scripts\python.exe -m product_writer examples/testo-510.input.json --output result/testo-510.json
.\.venv\Scripts\python.exe -m product_writer examples/testo-608-h1.input.json --format markdown --output result/testo-608-h1.md
```

На Linux/macOS команды такие же, путь к интерпретатору: `.venv/bin/python`. Результат без `--output` выводится в stdout. Диагностика идет в stderr; код завершения 0 означает успех, 2 означает ошибку. Выходной файл создается только после успешной генерации и проверки.

Проверка входного JSON без API и расходов:

```powershell
.\.venv\Scripts\python.exe -m product_writer examples/incomplete.input.json --validate-only
.\.venv\Scripts\python.exe -m pytest -q
```

Все автоматические тесты автономны: HTTP-запросы в них заменены транспортом `httpx.MockTransport`. Сохраненные результаты двух товаров получены отдельными реальными запусками через DeepSeek, не тестовыми заглушками. Сведения о модели, запросах и расходе токенов сохранены в `meta` каждого JSON.

## Входной контракт

Один JSON-объект на вызов. См. реальные входы `examples/testo-510.input.json` и `examples/testo-608-h1.input.json`.

| Поле | Тип | Поведение |
| --- | --- | --- |
| `name` | непустая строка | Обязательно; до 200 символов |
| `manufacturer` | строка или null | Пустое или отсутствующее значение попадает в список уточнений |
| `specs` | объект: название → строка или null | До 50 характеристик; значения с единицами и условиями |
| `description` | строка или null | Назначение или фрагмент паспорта; до 15 000 символов |
| `expected_specs` | список строк | Какие характеристики необходимо проверить на полноту для этого вида прибора |
| `sources` | список строк | Ссылки на исходные сведения; сохраняются в результате, сервис их не открывает |

`specs` и `expected_specs` могут отсутствовать. Пустая строка, null и явные отметки "данных нет", "нет данных", "не указано", "неизвестно" в характеристике считаются пропуском. Нулевое значение следует передавать строкой с единицами, например `"0 В"`: оно не считается пропуском. Числа без единиц, массив вместо объекта, лишние поля, повторяющиеся ключи JSON, NaN и некорректный JSON отклоняются. Файл ограничен 100 КБ; UTF-8 BOM поддерживается.

Если характеристики отсутствуют целиком, сервис сообщает об этом, не подставляя универсальный набор параметров. Для точного списка уточнений передайте `expected_specs`: интерфейсы или класс точности нужны не каждому прибору.

## Выходной контракт

1. `seo_title`: до 70 символов.
2. `seo_description`: 800–1200 символов **с пробелами**, после удаления внешних пробелов; длина считается `len()` в Python. Это длинное SEO-описание по условию задания, а не HTML meta description.
3. `key_specs`: список с названием, значением и указанием поля входа. Значения копируются без генерации, пересчета единиц или округления. Для неизвестных значений выводится "данных нет".
4. `search_queries`: 3–5 различных запросов.
5. `commercial`: короткое описание аудитории и задачи для менеджера.
6. `missing_fields`, `warnings`: обнаруженные пропуски и уточнения.
7. `sources`, `meta`: происхождение данных, модель, версия промпта, время UTC, длины и статистика API.

Поля `status: draft` и `needs_human_review: true` всегда присутствуют. Проверка LLM снижает риск ошибки, но не делает карточку автоматически утвержденной.

## Как устроена обработка

```text
JSON → валидация Product → генерация DeepSeek (JSON mode)
     → схема Draft + длины + поиск новых чисел
     → отдельная проверка фактов DeepSeek
     → копирование specs из входа → JSON / Markdown
```

1. `models.py` проверяет вход и выход через Pydantic; неизвестные поля запрещены.
2. `prompts.py` содержит полный текст двух промптов и их версию. Генератор получает вход как данные, список пропусков и контракт результата. Запрещены внешние знания, расшифровка маркировки, выдуманные преимущества, цена, наличие и прочие неподтвержденные обещания.
3. `service.py` проверяет длины и новые числовые токены. Отдельный запрос проверяет связь значений с параметрами, условия погрешности, назначения и качественные свойства во всех текстовых полях.
4. Если формат или содержание не проходят проверку, выполняется одна повторная генерация. Модель получает предыдущий черновик и причину отклонения, включая измеренную длину описания. После повторного отказа результат не экспортируется. Обычно нужны два логических запроса; максимум четыре при исправлении.
5. `llm.py` использует официальный OpenAI-совместимый endpoint DeepSeek. JSON mode не гарантирует схему, поэтому схема проверяется локально. SDK повторяет временные транспортные ошибки, 429 и серверные ошибки до двух раз; таймаут отдельного запроса 60 секунд. Временные повторы могут увеличить общее время выполнения и число HTTP-запросов.
6. `export.py` создает Markdown, экранируя разметку входных данных. `cli.py` отвечает за файлы, настройки, stdout/stderr и коды завершения.

Схема не требует базы данных, веб-сервера, очередей, CMS или векторного поиска. Для двух товаров CLI сокращает установку и дает воспроизводимые команды. Объектный сервис `generate(product, llm)` можно вызвать из будущего HTTP-обработчика без изменения логики.

## Данные и два примера

Выбраны товары из предоставленного YML магазина: testo 510, offer ID `58444`, и testo 608-H1, offer ID `72404`. Выгрузка от 03.11.2026 содержит названия и производителя, но не описания и технические характеристики. Поэтому входные данные вручную дополнены с соответствующих карточек того же магазина, а ссылки и исходные таблицы сохранены.

1. `examples/testo-510.input.json` → `examples/testo-510.result.json` и `examples/testo-510.result.md`.
2. `examples/testo-608-h1.input.json` → `examples/testo-608-h1.result.json` и `examples/testo-608-h1.result.md`.
3. `examples/incomplete.input.json`: отдельный пример неполного входа, не реальная модель товара.
4. `examples/sources/`: выдержка из YML, исходные таблицы и пояснения к подготовке входов.

Происхождение, нормализация обозначений и исключенные спорные формулировки описаны в `examples/sources/README.md`. Цена, наличие, доставка и статус поверки не включены: для этих демонстраций они не нужны и могут измениться.

## Обработка ошибок

Некорректный вход обнаруживается до API-вызова. Недостающий ключ, ошибки авторизации, баланс, лимиты, сетевые ошибки, таймауты, пустой ответ, незавершенный ответ и невалидный JSON приводят к понятной ошибке. Сырые исключения API, ключ и тело ответа поставщика не печатаются. Ключи не сохраняются в статистике или примерах.

Повторная генерация служит для исправления формата/содержания. Она не маскирует проблемы авторизации и оплаты. При ошибке старый файл результата не заменяется; смотрите код завершения команды, чтобы не принять старый файл за новый результат.

## Ограничения и улучшения

1. Семантическая проверка вероятностная: модель может пропустить неверное качественное утверждение или зависимость между параметрами. Проверка новых чисел не выявляет замену единиц и перестановку уже известных чисел; для этого нужен семантический этап и проверка человеком. Гарантируется только точное копирование структурированных характеристик.
2. Сервис доверяет исходным сведениям; он не проверяет паспорт, конкретную модификацию или актуальность сайта. Противоречия во входе могут быть выявлены моделью, но полнота обнаружения не гарантируется.
3. Бедный вход иногда не позволяет создать полезные 800–1200 символов. Сервис запрашивает уточнения или отказывает после двух попыток, вместо тихого выпуска невалидного текста. Он не использует локальный шаблон как подмену ответа API.
4. Защита от инструкций в товарном описании состоит из разделения ролей, запретов в промпте, локальных проверок и независимого запроса проверки. Это не формальное доказательство устойчивости к prompt injection. Модели не даны инструменты, доступ к файлам или сети.
5. Два запроса одной модели могут иметь общие ошибки. Следующие шаги: корпус проверочных примеров с разметкой, словарь параметров по категориям, проверка единиц и условий, более строгие ссылки каждого утверждения на исходный факт, измерение доли неподтвержденных утверждений.
6. В MVP нет пакетной обработки всей выгрузки, интерактивного редактора, кеша, контроля бюджета и истории согласований. Для эксплуатации нужны также политика обработки данных и управление ключами. В API передаются только данные переданного товара.

## Проверка и зависимости

Проверены не только успешные ответы, но и границы длины, новые числа, неверная привязка известного числа к параметру, повторная генерация, отказ проверки фактов, пустые поля, неверный JSON, HTTP-ошибки, таймауты, безопасная диагностика, UTF-8 BOM и защита входного файла от перезаписи. Транспортные тесты проверяют фактическое тело HTTP-запроса SDK.

Версии среды и итоговые результаты запуска записаны в `VALIDATION.md`. `constraints.txt` фиксирует версии проверенного чистого окружения; это ограничения версий, а не файл с локальными путями. Тесты не доказывают качество семантической проверки настоящей LLM; сохраненные реальные примеры дополнительно проверены по входам.
